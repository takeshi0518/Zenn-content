# はじめに

https://zenn.dev/ashunar0/articles/cc351badf8681c

以前から Zenn で気になっていた、こちらの記事に触発され**Hono × Inertia.js × React による SPA の新体験**を味わうため試してみました。

ちょうど Hono × React で簡単な Todo アプリを作成していたので、それと比較させてみると、見た目も機能も同じものを作ったつもりが、書くコードがほとんど別物になりました。

:::message
**まとめ**
同じ Todo アプリを、SPA + REST API と Inertia.js の 2 つの構成で実装しました。
ユーザー体験はほぼ同じだが、更新後の画面を組み立てる場所が大きく異なりました。

- SPA + REST API 版では、サーバーから受け取った処理結果をクライアントの状態へ合成する
- Inertia.js 版では、サーバーがページ単位の props を組み立て、Inertia がそれを使って現在のページを更新します
- その結果、API を呼び出すための fetch や、サーバー由来データの同期コードが減りました
- 単一アプリとして配備したことで、CORS 設定や二段階のデプロイも不要になりました
- 今回の Inettia.js 版では、POST 後に GET が追加され、リクエスト回数と転送量が増えた本質的な違いは、「サーバーの最新状態から、更新後の画面を誰が組み立てるか」にあります。

:::

# 前提

比較対象は、以前作った hono-todo という Todo アプリ。

https://github.com/takeshi0518/hono-todo

Hono + Cloudflare Workers + D1 + React + Vite で構築した SPA + REST API 構成のフルスタック Todo アプリです。
今回はこれと同じものを、Inertia.js を使って作り直しました。

https://github.com/takeshi0518/hono-todo-inertia

言語・機能・UI を揃え、主にアプリケーション構成とデータの受け渡し方を変えて比較しました。
こうすることで、実装に現れた違いを構成の違いから考えやすくしています。

なお Inertia 版では、D1 への接続と本番デプロイは行っていません。
今回注目しているリクエスト回数の違いはローカル環境でも確認できるため、通信パターンの比較には支障がないと判断しました。

ただし、今回の実装のまま D1 に接続した場合、Inertia.js 版では「書き込み → 更新後の一覧の読み直し」となり、DB アクセスが 2 回発生します。
また今回の実装では更新後に Todo 全件を返すため、件数が増えた場合の転送量については未検証です。
本番環境では、この差がより大きくなる可能性があります。

# Inertia.js とは何か

Inertia.js はフレームワークではありません。
既存のバックエンドフレームワークと React / Vue / Svelte などのフロントエンドをつなぐ仕組みです。
大きく見ると、次の２つで成り立っています。

1. サーバーとクライアントの間の取り決め
2. それを各フレームワークで利用するためのアダプタ

初回アクセスでは、サーバーは page object を埋め込んだ HTML を返します。
その後の画面遷移では、Inertia が通常のページ遷移を横取りし、JavaScript からサーバーへリクエストを送ります。
サーバーは`component`、`props`、`url`などを含む JSON の page object を返します。

クライアントは `component` の名前から実際の React コンポーネントを見つけ、
受け取った props とともに現在のページを差し替えます。

ルーティングや認証、データ取得などはサーバー側に残したまま、
フルページリロードをせずに SPA のような画面遷移を実現する仕組みです。

Inertia.js は Laravel との組み合わせで広く使われていますが、
Rails、Django、Phoenix などのサーバーアダプタもあります。

公式が Inertia.js を「現代のモノリス」と呼ぶのは、
フロントエンドとバックエンドを独立したアプリに分けず、
サーバー主導の構成を保ったまま SPA の体験を実現する設計思想だからです。

そして 2026 年 4 月、Hono 公式の middleware として
`@hono/inertia` が追加されました。

# 何が変わったのか

SPA + REST API 構成の Todo アプリ(hono-todo)と比較して変わった点が３つあるので紹介します。

## 1. オリジンが１つになった

hono-todo ではフロントエンドを Cloudflare Pages、API を Cloudflare Workers にデプロイしていたため、両者は別オリジンでした。ブラウザの Same-Origin Policy により、API 側で CORS を設定しないとレスポンスを JavaScript から読めません。
しかし Inertia.js 版ではオリジンが１つなので CORS の制約が無く設定ファイルから２つの環境変数が消えました。
また、hono-todo ではフロントをデプロイして URL が確定してから、API 側の設定を変え再デプロイしていました。この手順がごっそり無くなりました。
デプロイ先が 2 つから 1 つになったのも大きな変化です。

これは Inertia.js の page object の仕組みそのものによるものではなく、今回フロントエンドとバックエンドを単一アプリ・単一オリジンにまとめたことで生まれた変化です。

## 2. Todo 一覧を手元で更新するコードがなくなった

hono-todo では**Todo 一覧の表示状態をクライアント**で持っていました。そのため作成・更新・削除のたびに、サーバーへのリクエストとは別に、手元の配列を最新の状態へ更新する必要があります。

```typescript
const res = await fetch ('/todos', { method: 'POST', ... });
const newTodo = await res.json();
setTodos([...todos, newTodo]); //手元の配列を最新状態に更新
```

Inertia.js 版ではこの作業がなく下記のような処理で一覧が更新されます。

1. POST /todos → サーバーがデータを更新し、303 を返す
2. Inertia がリダイレクトを追跡して GET / を投げる
3. GET /が更新後の todos を props にして c.render する
4. Inertia が新しい page object を受け取り、一覧が再描画される

```typescript
//クライアント側
router.post('/todos', { title: todoContent });

//サーバー側
let todos: Todo[] = [
  { id: 1, title: 'todo1', completed: false },
  { id: 2, title: 'todo2', completed: false },
];

app.get('/', (c) => {
  return c.render('Todos/Index', { todos });
});

app.post('/todos', async (c) => {
  const nextId = todos.reduce((maxId, todo) => Math.max(maxId, todo.id), 0) + 1;
  const { title } = await c.req.json();
  todos.push({ id: nextId, title, completed: false });

  return c.redirect('/', 303);
});
```

```tsx
//コンポーネント側
export default function Index({ todos }: { todos: Todo[] }) {
  // useState も useEffect も fetch もない
  return <ul>{todos.map(...)}</ul>
}
```

## 3. エラーも page props になった

hono-todo では、成功と失敗をクライアント側で判定していました。

```text
成功:
レスポンスからTodoを受け取る
→ setTodos で一覧を更新

失敗:
res.ok を確認する
→ catch
→ setError でエラー状態を更新
```

```typescript
//従来のSPA

export async function addTodo(title: string): Promise<Todo> {
  const response = await fetch(`${url}/todos`, { ... });

  if (!response.ok) {
    throw new Error(`todoの登録に失敗しました: ${response.status}`)
  }

  return response.json();
}

const createTodo = async (title: string) => {
  try {
    const newTodo = await addTodo(title);
    setTodos((prev) => [...prev, newTodo])
  } catch (err) {
    console.error(err);
    setSubmitError('todoの登録に失敗しました');
  } finally { ... }
}
```

Inertia.js 版ではバリデーションもページを描画するための props として返します。

```typescript
//Inertia版

app.get('/', (c) => {
  return c.render('Todos/Index', { todos });
});

app.post('/todos', zValidator('json', createTodoSchema, (result, c) => {
  if (!result.success) {
      return c.render('Todos/Index', {
        todos,
        errors: toFieldErrors(result.error), //エラーメッセージを抽出する関数
      });
    }
}),
(c) => {
  ...
  return c.redirect('/', 303);
 }
);

```

```text
成功:
POST → 303 → GET / → { todos }
失敗:
POST               → { todos, errors }
```

HTTP 上の経路は異なりますが、最終的にクライアントが受け取るのは、
どちらも「その時点でページを描画するための page object」です。

hono-todo ではクライアントがレスポンスを見て
`setTodos`を`setError`を使い分けていました。

Inertia.js 版ではサーバーが`todos`や`errors`を props として組み立てるため、
クライアント側でレスポンスを表示状態へ変換するコードがなくなりました。

# なぜそうなるか

hono-todo も Inertia.js 版も、Todo の正しい状態を持っているのはサーバーです。
違うのは、**サーバーの状態から更新後のページを誰が組み立てるか**です。
hono-todo では、サーバーが更新結果を返し、クライアントがそれを現在の表示状態へ反映します。
Inertia.js 版では、サーバーが更新後のページに必要な props を組み立て、Inertia がそれを画面へ反映します。

## 1. hono-todo - サーバーは差分を返す

今回の hono-todo では、更新後のページ全体ではなく、操作によって生じた結果を返します。
ここではこれを「差分」と呼びます。
hono-todo で`POST /todos`を投げたときのレスポンスは下記の通りです。

```json
{ "id": 3, "title": "todo3", "completed": false }
```

そして返ってきた todo を クライアントが持っている一覧へ反映します。
つまりサーバーから返ってくる値は**差分**です。
この差分をクライアントの状態に反映するのですが、その反映の仕方は操作ごとに違います。

```typescript
setTodos([...todos, newTodo]); // 作成 → 末尾に足す
setTodos(todos.map((t) => (t.id === id ? { ...t, completed } : t))); // 更新 → 該当を置き換える
setTodos(todos.filter((t) => t.id !== id)); // 削除 → 該当を除く
```

## 2. Inertia.js - サーバーは完成品を返す

一方、今回の Inertia.js 版では、更新後のページを描画するために必要な props 一式が返ります。
ここではこれを「完成品」と呼びます。
Inertia.js で`router.post('/todos', { title: todoContent })`を実行すると下記のレスポンスが返ってきます。(前述のとおり POST は 303 を返すので、これは追跡された`GET /`のレスポンスです)

```json
{
  "component": "Todos/Index",
  "props": {
    "todos": [
      { "id": 1, "title": "todo1", "completed": false },
      { "id": 2, "title": "todo2", "completed": false },
      { "id": 3, "title": "todo3", "completed": false }
    ]
  },
  "url": "/",
  "version": null
}
```

そして返ってきた props を受け取り画面に表示させます。
つまりサーバーから返ってくる値は**完成品**です。
更新後の props が page object として渡ってくるため、アプリ側で「既存の todos にどう反映するか」を書く必要がありません。

```tsx
export default function Index({ todos }: { todos: Todo[] }) {
  return (
    <ul>
      {todos.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
    </ul>
  );
}
```

## 3. なぜクライアントの同期コードが消えるのか

### 差分を受け取る場合

hono-todo では、サーバーから返ってきた結果を現在の表示状態へ反映するのはクライアントの責任です。
作成なら追加、更新なら置き換え、削除なら除外します。

```typescript
setTodos([...todos, newTodo]); //作成
setTodos(todos.map((t) => (t.id === id ? { ...t, completed } : t))); //更新
setTodos(todos.filter((t) => t.id !== id)); //削除
```

この処理には、`todos`が配列であること、Todo に`id`があること、作成時には末尾へ追加することなど、アプリ固有の知識が含まれています。
つまりクライアントは、サーバーで起きた変更を受け取るだけでなく、その変更を自分の表示状態へどう同期するかまで知っている必要があります。

### page object(完成品)を受け取る場合

Inertia.js 版では、その「どう同期するか」をアプリ側で書く必要がありません。
サーバーが更新後の`todos`を含む page object を組み立てます。クライアント側の Inertia は、それが Todo なのか User なのかを理解する必要がありません。

```json
{
  "component": "Todos/Index",
  "props": {
    "todos": [
      { "id": 1, "title": "todo1", "completed": false },
      { "id": 2, "title": "todo2", "completed": false },
      { "id": 3, "title": "todo3", "completed": false }
    ]
  },
  "url": "/",
  "version": null
}
```

受け取った page object を現在のページへ適用します。
基本的な更新単位を page object に揃えられるため、Inertia は`todos`の構造や更新ルールを知らなくても処理できます。

```tsx
export default function Index({ todos }: { todos: Todo[] }) {
  return (
    <ul>
      {todos.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
    </ul>
  );
}
```

### 状態管理は消えていない

React DevTools を見ると、Inertia 自身も page の状態を保持しています。つまり状態管理そのものが消えたわけではありません。
ただし Inertia の更新ロジックには、`Todo` や `id`、作成時は配列へ追加するといったアプリ固有の知識はありません。`todos` は `page.props` の中に含まれていますが、Inertia にとっては page object の一部にすぎません。

hono-todo では、サーバーの変更をクライアント側で再現していました。
Inertia.js 版では、サーバーが更新後のページ状態を組み立てるため、クライアントはその変更を再現する必要がありません。
つまり状態管理がなくなったのではなく、サーバーとクライアントの状態を同期するアプリ固有のコードが減ったのです。

> **Inertia.js で消えたのは状態管理ではなく**、サーバーで起きた変更をクライアント側でもう一度再現するための同期コードでした。
> SPA + REST API 版ではクライアントが更新後の表示状態を組み立てていましたが、Inertia.js 版ではサーバーが page props を組み立てます。
> なお、CORS やデプロイ先が 1 つになったことはこの仕組みとは別で、フロントとバックエンドを単一アプリとして構成したことによる変化です。

# トレードオフ

## 単純さと通信コスト

前章では、更新後の page object をサーバーが組み立てることで、クライアント側の同期コードを減らせることを見てきました。
一方、その最も単純な実装では、SPA + REST API 版より通信回数や転送量が増えます。
この単純さと通信コストの関係を実際に確認してみます。

Inertia.js 版では、更新に`POST`とリダイレクト後の`GET`が直列に発生します。
hono-todo は`POST /todos`の 1 リクエストだけで更新が完了します。

この差がどれくらい効くのか、ローカルで計測しました。

※この計測はローカル環境で、Inertia.js 版は DB に接続していません。
そのため本番環境の性能比較ではなく、直列するリクエスト数の違いが
待ち時間にどう現れるかを見るための計測です。

|           | リクエスト                             | サイズ      | No throttling  | 3G                  |
| --------- | -------------------------------------- | ----------- | -------------- | ------------------- |
| hono-todo | `POST /todos` 1 本(201)                | 0.3KB       | 13ms           | 2.02s               |
| Inertia   | `POST /todos` 303 → `GET /`200 の 2 本 | 0.2 + 0.4KB | 47 + 21 = 68ms | 2.04 + 2.01 = 4.05s |

かなり極端な条件ですが、通常時と 3G にスロットリングした場合で比較しました。
通常時は 13ms と 68ms で、体感としてどちらも一瞬です。
一方、3G では約 2 秒と約 4 秒になり、直列するリクエスト数の違いが
待ち時間の差としてはっきり現れました。

転送量にも違いがあります。
今回の Inertia.js 版では、更新後の `GET /` で Todo 全件を返しているため、
件数に比例してレスポンスサイズが増えます。

一方、hono-todo は作成した 1 件だけを返すため、
Todo の総件数が増えても POST レスポンスのサイズはほぼ変わりません。

### Inertia.js にも最適化手段がある

ここまでの計測は、更新後に page object をそのまま再取得する今回の実装についてのものです。
Inertia.js には Partial reload、Deferred props、Merge props などの最適化手段があり、`@hono/inertia` もこれらに対応しています。

`@hono/inertia`の README では、必要な props だけを再取得する Partial reloads、重い props の取得を後回しにする Deferred props、既存の props にデータを追加する Merge props / Infinite scroll などが紹介されています。

これらを使えば、今回のように毎回すべてのデータを返す必要はありません。
一方で、最適化を進めると「どの props を再取得するか」「取得したデータをどう合成するか」といった情報が必要になります。

これは前章で見た、page object をそのまま適用できる単純なモデルから少し離れることでもあります。
今回はこれらの機能を実装・計測していないため、性能がどの程度改善するかまでは検証していません。ここでは「Inertia.js にも通信コストを調整する手段がある」という紹介に留めます。

# まとめ

同じ Todo アプリを作り比べてみて、一番大きく変わったのはコード量そのものではなく、「誰が更新後の画面を組み立てる」といった責任の置き場所でした。
SPA + REST API 版では、サーバーから返された結果をクライアントが自分の表示状態へ同期します。
Inertia.js 版では、サーバーが更新後の page props を組み立て、クライアントはそれを受け取って描画します。その結果、`fetch`や`setTodos`のような、サーバーで起きた変更をクライアント側でもう一度再現するコードが減りました。
一方、その単純なモデルでは更新後の再取得が増えるため、通信コストとのトレードオフがあります。
必要であれば `Partial reload` や `Merge props` などで最適化できます。

## Inertia.js が向きそうな場面

Inertia.js が向いていそうなのは、サーバーの最新状態をもとにページを表示し直すことが自然なアプリです。
例えば、管理画面や CRUD 中心の業務アプリでは、「フォームを送信する → サーバーが更新する → 更新後の一覧や詳細画面を表示する」という流れが多くなります。
このようなアプリでは、サーバーで起きた変更をクライアント側でも setState で再現するより、サーバーが更新後の page props を返す方が単純に書けます。

## SPA + REST API が向きそうな場面

クライアント側の状態遷移そのものがユーザー体験の中心になるアプリでは、SPA + REST API の方が自然だと感じました。
例えばエディタやカンバンではドラッグ、などサーバーとの通信とは独立してクライアント内の状態が何度も変化します。
このような場合、クライアントが長く状態を保持し、必要なタイミングでサーバーと同期する設計の方が扱いやすくなります。
そしてもうひとつが、API を Web 以外からも利用する場合です。
モバイルアプリ、CLI、外部サービスなどが挙げられます。

## TypeScript × Hono × Inertia.js について

Hono と React の両方を TypeScript で書けるため、`c.render` に渡した props の型をページコンポーネント側までつなげられるのも面白い点です。
異なる言語間でもコード生成などで型を共有する方法はありますが、`@hono/inertia` では同じ TypeScript の世界の中で page props を型付けできます。

ただし今回試した範囲では、1 ページに複数の `c.render` があると props の型が union になり、扱いづらく感じる場面もありました。そのため今回は利用を見送りました。

`@hono/inertia` の README でも end-to-end type safety が特徴として挙げられています。2026 年 4 月に登場したばかりの middleware なので、TypeScript でサーバーとフロントの両方を書ける Hono ならではの使い方が今後どう発展するのか注目したいです。

## さいごに

今回 Inertia.js に触れて特に面白かったのは、自分がこれまで知っていた SPA とは、Web アプリの組み立て方そのものが違って見えたことです。
自分はこれまでほぼ TypeScript の世界で Web 開発をしてきたため、Laravel や Rails を中心としたサーバーサイドの文化にはあまり触れてきませんでした。Inertia.js との出会いも今回が初めてです。
PHP や Ruby を書けるようになり、それらのエコシステムに触れれば、今回とはまた違った見方ができるのかもしれません。

技術を知ることは、単に使える道具が一つ増えるだけではなく、「こういう作り方もある」と選択肢そのものが増えることだと思います。選択肢が増えれば、目の前の問題に対して「いつもの方法」以外からも技術を選べるようになります。

今回の Inertia.js も、自分にとってそんな新しい選択肢の一つでした。
知らない技術に触れるたびに、それまで当たり前だと思っていた設計が、実は数ある選択肢の一つだったと気づきます。そこからまた新しい世界が広がっていく。
**自分にとっては、そこがこの世界の面白いところです。**
これからも知的好奇心を大切に、知らないことを楽しみながら学び続けていきたいと思います。

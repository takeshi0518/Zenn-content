# はじめに

https://zenn.dev/ashunar0/articles/cc351badf8681c

以前から Zenn で気になっていた、こちらの記事に触発され**Hono × Inertia.js × React による SPA の新体験**を味わうため試してみました。

ちょうど Hono × React で簡単な Todo アプリを作成していたので、それと比較させてみると、見た目も機能も同じものを作ったつもりが、書くコードがほとんど別物になりました。

:::message
**まとめ**
同じ Todo アプリを、SPA + REST API と Inertia.js の 2 つのアーキテクチャで実装しました。
ユーザー体験はほぼ同じだが、開発体験が大きく違いました。

- API エンドポイント、CORS 設定、状態の同期コードが消えた
- 代わりに、操作のたびにサーバー往復が発生している
- この違いはすべて「サーバーが差分を返すか、完成品を返すか」という 1 つの選択から派生している

:::

# 前提

比較対象は、以前作った hono-todo という Todo アプリ。

https://github.com/takeshi0518/hono-todo

Hono + Cloudflare Workers + D1 + React + Vite で構築した SPA + REST API 構成のフルスタック Todo アプリです。
今回はこれと同じものを、Inertia.js アーキテクチャで作り直しました。

https://github.com/takeshi0518/hono-todo-inertia

言語・インフラ・機能・UI をすべて揃え、**変えたのはアーキテクチャだけ**です。
こうすることで、差がでたときの原因をアーキテクチャに絞ることができます。
なお Inertia 版では D1 への接続とデプロイを行っていません。往復回数の差はローカルでも観測できるため、結論は変わらないと判断しました。

ただし D1 を繋ぐと、Inertia.js 版は「書き込み → 読み直し」で DB アクセスが 2 回になります。また毎回全件を返すため、件数が増えたときの転送量も未検証です。この点は差が広がる可能性があります。

# Inertia.js とは何か

Inertia.js はフレームワークではありません。実体は２つだけです。

1. サーバーとクライアントの間の取り決め
2. それを実装したアダプタ

サーバーは HTML でも JSON でもなく、「コンポーネント名 + props」を返します。クライアントはその名前から実際のコンポーネントを解決して描画する。ルーティングもデータ取得もサーバー側に残したまま、画面遷移だけを SPA のように差分更新する仕組みです。

Laravel エコシステムから生まれたもので、Rails 版・Django 版などもあります。公式が「現代のモノリス」と呼ぶのは、フロントとバックを分けずに 1 つのアプリとして作る、という主張だからです。

そして今年 4 月、Hono 公式から `@hono/inertia` がリリースされました。

# 何が変わったのか

SPA + REST API 構成の Todo アプリ(hono-todo)と比較して変わった点が３つあるので紹介します。

## 1. オリジンが１つになった

hono-todo ではフロントエンドを Cloudflare Pages、API を Cloudflare Workers にデプロイしていたため、両者は別オリジンでした。ブラウザの Same-Origin Policy により、API 側で CORS を設定しないとレスポンスを JavaScript から読めません。
しかし Inertia.js 版ではオリジンが１つなので CORS の制約が無く設定ファイルから２つの環境変数が消えました。
また、hono-todo ではフロントをデプロイして URL が確定してから、API 側の設定を変え再デプロイしていました。この手順がごっそり無くなりました。
デプロイ先が 2 つから 1 つになったのも大きな変化です。

## 2. useState も fetch もない

hono-todo では**状態をクライアント**で持っていました。そのため作成・更新・削除のたびに、サーバーへのリクエストとは別に、手元の配列を最新の状態に直す作業が必要です。

```typescript
const res = await fetch ('/todos', { method: 'POST', ... });
const newTodo = await res.json();
setTodos([...todos, newTodo]); //手元の配列を最新状態に更新
```

Inertia.js 版ではこの作業がなく下記のような処理で一覧が更新されます。

1. POST /todos → サーバーがデータを更新し、303 を返す
2. Inertia がリダイレクトを追跡して GET / を投げる
3. サーバーが更新後の全件で c.render
4. props が差し替わり、一覧が再描画される

```typescript
//クライアント側
router.post('/todos', { title: todoContent });

//サーバー側
let todos: Todo[] = [
  { id: 1, title: 'todo1', completed: false },
  { id: 2, title: 'todo2', completed: false },
];

app.get('/', (c) => {
  return c.render('Todos/Index', { todos });
});

app.post('/todos', async (c) => {
  const nextId = todos.reduce((maxId, todo) => Math.max(maxId, todo.id), 0) + 1;
  const { title } = await c.req.json();
  todos.push({ id: nextId, title, completed: false });

  return c.redirect('/', 303);
});
```

```tsx
//コンポーネント側
export default function Index({ todos }: { todos: Todo[] }) {
  // useState も useEffect も fetch もない
  return <ul>{todos.map(...)}</ul>
}
```

## 3. 成功と失敗が同じ経路

hono-todo では成功したときにはデータを返し、失敗したときはエラーを投げます。
これは別々のルートであり、クライアント側で分岐が必要です。

```typescript
//従来のSPA

export async function addTodo(title: string): Promise<Todo> {
  const response = await fetch(`${url}/todos`, { ... });

  if (!response.ok) {
    throw new Error(`todoの登録に失敗しました: ${response.status}`)
  }

  return response.json();
}

const createTodo = async (title: string) => {
  try {
    const newTodo = await addTodo(title);
    setTodos((prev) => [...prev, newTodo])
  } catch (err) {
    console.error(err);
    setSubmitError('todoの登録に失敗しました');
  } finally { ... }
}
```

Inertia 版では成功も失敗も c.render()を実行して「次に表示すべき画面」を返しています。
状態の真実をサーバーで持っているので「いま表示すべき画面」を知っています。
そのため、成功時でも失敗時でも同じ経路を辿って返すことができます。

```typescript
//Inertia版

app.get('/', (c) => {
  return c.render('Todos/Index', { todos });
});

app.post('/todos', zValidator('json', createTodoSchema, (result, c) => {
  if (!result.success) {
      return c.render('Todos/Index', {
        todos,
        errors: toFieldErrors(result.error), //エラーメッセージを抽出する関数
      });
    }
}),
(c) => {
  ...
  return c.redirect('/', 303);
 }
);

```

```text
成功: POST → 303 → GET / → c.render('Todos/Index', { todos })
失敗:              POST  → c.render('Todos/Index', { todos, errors })
```

このように並べると、失敗はリダイレクトを省略しているだけで、最後に返るものは同じ形です。なぜ失敗時にリダイレクトされないのかというと、リダイレクトすると`errors`が消えてしまいます。`GET /`は`errors`を知らないので直接`c.render`するようにします。

また、エラーがステータスコードではなく props になった点も大きい変化です。
hono-todo では`res.ok`で分岐して`setError`、Inertia.js は`errors`が props で届きます。エラーの置き場所が state から props に変わりました。

# なぜそうなるか

ここまで３つの違いを挙げましたが、原因は 1 つです。
それは「**状態の真実をどこに置くか**」です。

## 1. hono-todo - サーバーは差分を返す

hono-todo で`POST /todos`を投げたときのレスポンスは下記の通りです。

```json
{ "id": 3, "title": "todo3", "completed": false }
```

そして返ってきた todo を useState の更新用関数を使って最新状態にします。
つまりサーバーから返ってくる値は**差分**です。
この差分をクライアントの状態に反映するのですが、その反映の仕方は操作ごとに違います。

```typescript
setTodos([...todos, newTodo]); // 作成 → 末尾に足す
setTodos(todos.map((t) => (t.id === id ? completed : t))); // 更新 → 該当を置き換える
setTodos(todos.filter((t) => t.id !== id)); // 削除 → 該当を除く
```

## 2. Inertia.js - サーバーは完成品を返す

Inertia.js で`router.post('/todos', { title: todoContent })`を実行したときのレスポンスは下記の通りです。

```json
{ "component": "Todos/Index", "props": { "todos": [全件] }, "url": "/", "version": null }
```

そして返ってきた props を受け取り画面に表示させる。
つまりサーバーから返ってくる値は**完成品**です。
完成品が props 経由で渡ってくるので、クライアントの状態に反映させる必要はありません。

```tsx
export default function Index({ todos }: { todos: Todo[] }) {
  return (
    <ul>
      {todos.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
    </ul>
  );
}
```

# 1. はじめに

自分のポートフォリオアプリである人材育成アプリを Vercel にデプロイしました。しかし本番環境での表示速度がかなり遅くて悩んでいました。一番最初に思いつくこととして、コードの最適化をしようと思いました。

:::message
**この記事のまとめ**

- Promise.all で並列化するとローカルで速くなった。でも本番環境の TTFB は誤差の範囲だった。
- 本当の原因は Vercel と Supabase のリージョンのズレであり、揃えると本番環境の TTFB が約 43%改善された。
- コードの最適化をする前に、インフラを確認するべきだった。
  :::

# 2. 課題発見

デプロイしてアプリを使ってみました。正直な感想は「表示速度が遅すぎる」「体感 2 秒くらい待たされている」というものでした。これは改善しないといけないと思い、後日調査することにしました。

# 3. コードを調べる

まずコードを調べました。
よくある改善点として**直列の非同期処理を並列化する**ことがあります。
前提として各非同期処理が依存関係でないという条件があり、このことを念頭に調査すると下記のようなコードがありました。

```jsx
export default async function AdminPage() {
  const { orgId, profile } = await requireAdmin(supabase);
  // 1つ目のクエリ：スタッフ一覧を取得
  const { data: staffs, error: staffError } = await supabase
    .from('profiles')
    .select('id, name, role, store_name, avatar_url, email')
    .eq('organization_id', orgId)
    .eq('role', 'staff');

  if (staffError) redirect('/admin');

  // 2つ目のクエリ：評価期間を取得
  const { data: evaluationPeriods, error: periodsError } = await supabase
    .from('evaluation_periods')
    .select('id, name, is_current')
    .eq('organization_id', orgId);
  // ...
}
```

スタッフ一覧を取得する処理と評価期間を取得する処理は依存関係にありません。2 つ目のクエリは 1 つ目のクエリの実行を待つ理由がないので、**Promise.all で並列化**してみることにしました。

# 4. 改善 ①

Promise.all を使って 2 つのクエリを並列化させました。
並列化させることにより、スタッフ一覧と評価期間取得のクエリが同時並行に実行されるので改善が期待できます。

```typescript
const [
  { data: staffs, error: staffError },
  { data: evaluationPeriods, error: periodsError },
] = await Promise.all([
  supabase
    .from('profiles')
    .select('id, name, role, store_name, avatar_url, email')
    .eq('organization_id', orgId)
    .eq('role', 'staff'),
  supabase
    .from('evaluation_periods')
    .select('id, name, is_current')
    .eq('organization_id', orgId),
]);

if (staffError) redirect('/admin');
if (periodsError || !evaluationPeriods) return;
```

![直列と並列の待ち時間の違い](/images/series_vs_parallel.png)

ローカル計測(console.time)

| ページ                            | Before   | After    | 改善幅     |
| --------------------------------- | -------- | -------- | ---------- |
| /admin                            | 10.72ms  | 4.832ms  | 約 55%短縮 |
| /admin/staff                      | 10.47ms  | 4.782ms  | 約 54%短縮 |
| /admin/staff/[staffId]            | 66.58ms  | 24.336ms | 約 63%短縮 |
| /admin/staff/[staffId]/evaluation | 17.929ms | 11.085ms | 約 38%短縮 |

図を見てもらえば分かりますが、直列は順番待ちで、並列は同時実行です。
そして大事な視点は**通信回数(クエリの本数)は変わらない。短くなるのは待ち時間だけ**です。
その効果を検証するためにクエリの前後に console.time を仕込み計測したところ、大幅な改善が確認できました。
しかし少しモヤっと感があります。
**「体感 3 秒くらい待たされたけど、ここで改善した数ミリ秒は桁が違う...。」**
とりあえず改善されたから効果は本番環境ででるはずと思い先に進みました。

# 5. ところが本番環境で

:::message
TTFB とは?
Time To First Byte の略。
ブラウザがリクエストを送ってから、最初の 1 バイトが返ってくるまでの時間。
:::

本番環境での計測方法はローカルと違い**TTFB**を計測しました。
結果は表をみての通り、ローカルでの改善がまるで無かったように改善幅は誤差の範囲でした。
「なんで...。並列化にした効果はどこへ...。」
と思いました。

本番 TTFB 計測(リージョン米国時点)

| ページ                            | Before | After  | 改善幅     |
| --------------------------------- | ------ | ------ | ---------- |
| /admin                            | 1.17s  | 1.265s | 誤差範囲内 |
| /admin/staff                      | 1.58s  | 1.145s | 約 28%短縮 |
| /admin/staff/[staffId]            | 1.135s | 1.14s  | 誤差範囲内 |
| /admin/staff/[staffId]/evaluation | 1.29s  | 1.16s  | 約 10%短縮 |

# 6. なぜ本番環境で効かなかったのか

気になったのはローカルと本番で**測っているものが違う**ことです。
ローカルでは、**クエリを投げてそれが返ってくるまで**の時間。
本番では、**ブラウザからサーバーにリクエストを送信してそれが返ってくるまで**の時間。

<!-- ![ローカル環境と本番環境の違い](/images/production_vs_local.png) -->

図をみると分かりやすいですが、計測している範囲が違います。
並列化による効果として Supabase の往復の時間は改善されます。
しかし改善幅は誤差の範囲です。
TTFB には ① と ⑤ が含まれます。
**つまりブラウザ →Vercel、Vercel→ ブラウザ**
例えば TTFB が 1 秒だとして、そのうち ①⑤(ブラウザ ⇄ サーバー)が 0.8 秒占めていたら、②③(Supabase 往復)はたった 0.2 秒です。この 0.2 秒を並列化で縮めても、全体の 1 秒はほとんど変わりません。
では、なぜ ①⑤ の通信にそんなに時間がかかっていたのか? 調べてみると、意外な原因が見つかりました。

# 7. 原因はリージョンのズレだった

通信まわりを Google などで調べるといくつか参考になる記事を見つけました。
その記事を読んでみると、**Vercel のデフォルトリージョンがアメリカで、それが遅延の原因になる**ということに辿り着きました。
自分の設定を確認すると、**Supabase=東京**、**Vercel=アメリカ**でした。
そしてブラウザはもちろん日本です。
**ブラウザ ⇄Vercel(アメリカ)で太平洋を 1 往復**、**さらに Vercel⇄Supabase(東京)でもう 1 往復。**合計２往復していました。

<!-- ![リージョンの違い](/images/pacific_roundtrip_before_after.png) -->

地理的な距離があるぶん、通信のたびに時間がかかっていました。
クエリを並列化にして改善されなかったその正体が、リージョンのズレだったと判明しました。

# 8. 改善 ②

Vercel のリージョンを東京にしました。
Vercel のダッシュボードからプロジェクト →Settings→Functions→Function Region から**Tokyo, Japan (Northeast) - ap-northeast-1 - hnd1**を選択し再デプロイすると適用されます。
僕はこちらから設定しました。

![vercelダッシュボード画像](/images/vercel_dashboard.png)

別の方法としては vercel.json を作成して下記のように記述し再デプロイすると設定されるようです。
`hnd1` は東京リージョンを指します。

```json
{
  "regions": ["hnd1"]
}
```

そしてリージョンを変更して TTFB を再測定すると劇的に改善されていました。
体感 2 秒待たされたのが**1 秒も感じさせないくらい**になっていました。

本番 TTFB 計測(リージョン変更後)

| ページ                            | リージョン米 | リージョン東京 | 改善幅     |
| --------------------------------- | ------------ | -------------- | ---------- |
| /admin                            | 1.265s       | 722.85ms       | 約 43%短縮 |
| /admin/staff                      | 1.145s       | 512.11ms       | 約 55%短縮 |
| /admin/staff/[staffId]            | 1.14s        | 653.60ms       | 約 43%短縮 |
| /admin/staff/[staffId]/evaluation | 1.16s        | 539.87ms       | 約 53%短縮 |

# 9. 学び

はじめはコードを疑いました。
しかしそれは**非同期処理が直列であることが問題**という一方的な決めつけでした。
もちろん間違いではなく、実際に効果はありました。しかし本当の原因はインフラでした。
まさに「**木を見て森を見ず**」です。
僕の問題解決の順序はミクロ(コード) → マクロ(全体)です。この流れではしらみつぶしのように細かく潰していくので非効率です。
しかし今回の教訓から、マクロ(全体) → ミクロ(コード)の順で問題を洗い出し、仮説を立て、原因を特定し解決したほうがはるかに効率がいいことに気が付きました。
**フロントエンド・バックエンド・インフラ・DB はすべて繋がっています。**
ひとつのシステムとして全体を意識し、俯瞰して見なければならないことの重要性に気がつけたことも、大きな経験でした。
これから問題があったときは、目の前のエラー文や不具合だけでなく、周辺の事情も調査し解決していこうと思います。
